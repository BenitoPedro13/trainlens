# ADR-004: Background Jobs & Sync: BullMQ + Redis

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

The platform needs background job processing for several workflows: initial bulk import of historical activities (paginated, rate-limited), webhook-triggered incremental syncs, analytics recalculation, and future scheduled tasks. We also need Redis for API response caching, so the job broker should ideally use the same infrastructure.

## Decision

Use **BullMQ with Redis** as the background job system, with separate queues per job type.

## Options Considered

| Option                | Pros                                                                                                                                     | Cons                                                              |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **BullMQ + Redis** ✅ | Battle-tested, NestJS has `@nestjs/bull`, retry logic, dead letter queues, priority queues, rate limiting, job visibility via Bull Board | Requires Redis (but already needed for caching)                   |
| **pg-boss**           | Uses Postgres as broker, no extra infra                                                                                                  | Less feature-rich, smaller ecosystem, weaker rate limiting        |
| **Inngest**           | Serverless-friendly, great dashboard UI                                                                                                  | Cloud dependency, cost at scale, vendor lock-in                   |
| **Temporal**          | Workflow orchestration, durable execution                                                                                                | Massively over-engineered for this use case, heavy infrastructure |

## Consequences

### Positive

- Single Redis instance serves both caching and job brokering
- BullMQ's built-in rate limiter is perfect for respecting Strava's API limits
- Dead letter queues capture permanently failed jobs for manual inspection
- Bull Board provides a web UI for monitoring queue health
- NestJS integration is first-class via `@nestjs/bull`

### Negative

- Redis is an additional service to operate (though lightweight)
- BullMQ stores job data in Redis, which is memory-bound; very large job payloads should be avoided

## Queue Architecture

| Queue              | Purpose                                   | Concurrency | Rate Limit                            |
| ------------------ | ----------------------------------------- | ----------- | ------------------------------------- |
| `activity-sync`    | Fetch and normalize individual activities | 5           | 100/15min (matches Strava)            |
| `bulk-import`      | Paginated historical import               | 1 per user  | Throttled to avoid Strava rate limits |
| `analytics-recalc` | Recalculate DailyMetrics, CTL/ATL/TSB     | 3           | None                                  |
| `webhook-ingest`   | Process incoming webhook events           | 10          | None                                  |

### Retry Policy

- 3 retries with exponential backoff: 30s, 2min, 10min
- After final failure, job moves to dead letter queue
- Token refresh failures pause the user's sync and trigger a notification
