# ADR-001: Monorepo Tooling: Turborepo + pnpm Workspaces

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

The platform has two applications (Next.js web, NestJS API) and several shared packages (database, types, UI components). We need a monorepo tool that handles dependency management, build orchestration, and caching across all packages without slowing down development.

## Decision

Use **Turborepo + pnpm workspaces** as the monorepo tooling layer.

## Options Considered

| Option                   | Pros                                                                                                         | Cons                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| **Turborepo + pnpm** ✅  | Fast incremental builds, zero-config caching, small footprint, great DX with Next.js/NestJS, built by Vercel | Less opinionated than Nx; more manual setup for generators         |
| **Nx**                   | Very feature-rich, generators, excellent dependency graph visualization                                      | Heavy, opinionated, steep learning curve, overkill for early stage |
| **pnpm workspaces only** | Simplest setup                                                                                               | No build pipeline orchestration; slows down as repo grows          |
| **Lerna + npm**          | Familiar to many teams                                                                                       | Largely superseded; slower than alternatives                       |

## Consequences

### Positive

- Parallel task execution across packages reduces CI time
- Remote caching (Vercel or self-hosted) means repeated builds are near-instant
- Minimal configuration: `turbo.json` pipeline definition is ~20 lines
- pnpm's strict node_modules hoisting prevents phantom dependencies
- Natural alignment with Vercel deployment (same company maintains both)

### Negative

- No built-in code generators (unlike Nx); scaffolding new packages is manual
- Team must understand the `turbo.json` pipeline model (inputs, outputs, dependsOn)

### Risks

- If Turborepo development stalls, migration to Nx is possible but non-trivial
