# ADR-002: Database: PostgreSQL with TimescaleDB Extension

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

Activity data is fundamentally time-series: each activity has a timestamp, and many analytics queries involve aggregating by time windows (weekly volume, rolling averages, year-over-year comparisons). We need a database that handles both relational data (users, connections, tokens) and time-series analytics efficiently.

## Decision

Use **PostgreSQL with the TimescaleDB extension** as the primary (and only) database.

## Options Considered

| Option                          | Pros                                                                                                                                                | Cons                                                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **PostgreSQL + TimescaleDB** ✅ | SQL familiarity, native time-series queries (downsampling, windowing), open source, self-hostable, full ORM support, single database for everything | Slightly more setup than plain Postgres                                                                  |
| **Plain PostgreSQL**            | Simplest, great ORM support                                                                                                                         | Time-series queries (aggregating by week/month, rolling windows) are verbose and slow without extensions |
| **MongoDB**                     | Flexible schema                                                                                                                                     | No SQL, aggregation pipelines are verbose, weaker analytical queries                                     |
| **InfluxDB**                    | Purpose-built time-series                                                                                                                           | Poor relational modeling (users, connections, tokens); would require two databases                       |
| **Supabase (hosted PG)**        | Fast to start, has auth and realtime                                                                                                                | Harder to self-host, vendor lock-in, less control over extensions                                        |

## Consequences

### Positive

- `time_bucket()` makes weekly/monthly aggregation a single function call
- Continuous aggregates pre-compute rollups automatically as data arrives
- Built-in compression reduces storage for older activity data
- ORM (Prisma, TypeORM) works unchanged since TimescaleDB is just a PG extension
- Single database simplifies ops, backups, and transactions

### Negative

- TimescaleDB hypertables must be created via raw SQL migrations (Prisma doesn't have native support)
- Some hosting providers don't support TimescaleDB; may need to self-host or use Timescale Cloud

### Risks

- If TimescaleDB is overkill for early scale, we're carrying extra complexity. Mitigation: the extension is invisible until you create hypertables, so early development can use plain PG tables and convert later.

## Implementation Notes

- Create hypertable on `Activity.startedAt` via a raw migration after Prisma creates the table
- Use continuous aggregates for weekly/monthly rollups on `DailyMetrics`
- Enable compression on activity data older than 6 months
