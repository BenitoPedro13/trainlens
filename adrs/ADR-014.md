# ADR-014: Data Lifecycle, Deletion & GDPR Compliance

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

The platform's core principle is "users own their data." This must be backed by concrete technical behavior: what happens when a user disconnects a provider, deletes their account, or requests a data export? If the platform serves EU users (likely, given the global fitness community), GDPR compliance is not optional. Even outside the EU, clear data lifecycle policies build trust with privacy-conscious athletes.

## Decision

Implement a **soft-delete model with a 30-day retention window** for account deletion. Provider disconnections give the user a choice to keep or remove synced data. Full data export is available on demand.

## User Actions and System Behavior

### Disconnect a Provider

| Step | Behavior |
|------|----------|
| User clicks "Disconnect Strava" | Revoke OAuth tokens immediately (call provider's revoke endpoint if available) |
| | Delete the `Connection` record (hard delete; tokens are gone) |
| | Prompt user: "Keep your synced activities or delete them?" |
| Keep | Activities remain in the database; `source` field still says 'strava' but no active connection |
| Delete | All activities with `source = 'strava'` for this user are hard-deleted; DailyMetrics recalculated |

### Delete Account

| Step | Behavior |
|------|----------|
| User requests account deletion | Set `User.deletedAt = now()` (soft delete) |
| | Immediately revoke all OAuth connections |
| | User is logged out; cannot log back in |
| | All API queries return 404 for this user |
| Grace period (30 days) | User can contact support to reverse the deletion |
| After 30 days | Background job hard-deletes: User, all Connections, all Activities, all ActivityRawPayloads, all DailyMetrics, all WebhookEvents referencing this user |

### Provider Sends Deauthorize Event

| Step | Behavior |
|------|----------|
| Strava sends `athlete.deauthorize` webhook | Handled the same as user-initiated disconnect |
| | Delete `Connection` record |
| | Notify user via email: "Strava was disconnected from your account" |
| | Activities are preserved by default (user can delete them manually) |

### Data Export (GDPR Article 20)

| Step | Behavior |
|------|----------|
| User requests data export | Background job generates a JSON archive containing: user profile, all activities (normalized), all DailyMetrics, connection metadata (without tokens) |
| | File is made available for download for 24 hours, then deleted |
| | Export is rate-limited (1 per 24 hours) to prevent abuse |

## Schema Support

```prisma
model User {
  // ...
  deletedAt   DateTime?  // null = active; set = soft-deleted
}

model Connection {
  // ...
  user  User @relation(fields: [userId], references: [id], onDelete: Cascade)
}

model Activity {
  // ...
  user  User @relation(fields: [userId], references: [id], onDelete: Cascade)
}
```

Cascading deletes ensure that when a User is hard-deleted, all related records are removed in a single transaction.

## Cleanup Background Job

Runs daily:
1. Find all users where `deletedAt < now() - 30 days`
2. Hard-delete each user and all cascading records
3. Log the deletion for audit purposes (anonymized: user ID only, no PII)

## Consequences

### Positive
- Users have clear control over their data
- Soft delete prevents accidental permanent loss (30-day undo window)
- Data export satisfies GDPR Article 20 (right to data portability)
- Cascading deletes ensure no orphaned records
- Clear separation between provider disconnection and account deletion

### Negative
- Soft-deleted users still occupy database space for 30 days
- Every query must filter out soft-deleted users (`WHERE deletedAt IS NULL`)
- Data export job can be resource-intensive for users with thousands of activities

### Risks
- If cascading deletes miss a table, orphaned PII could remain. Mitigate with integration tests that verify complete deletion.
