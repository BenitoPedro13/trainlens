# ADR-018: AI-Generated Workout Insights

> **Status:** Proposed (provider not yet selected)
> **Date:** 2026-05-20

## Context

Strava's "Athlete Intelligence" feature generates short natural-language summaries of each workout: highlights, comparisons to recent training, and gentle coaching tips. It is one of the most-discussed differentiators in their subscription tier.

TrainLens can do this and arguably better, because we already compute the analytical primitives (TSS, zones, CTL/ATL/TSB, best efforts, training monotony). An LLM with structured access to those primitives can generate insights that are factually grounded rather than vague platitudes.

The architectural question is not "should we do this" but "how, with which provider, and at what cost."

## Decision

Build an **LLM-agnostic insights service** behind a provider interface, similar to the `FitnessProvider` pattern in ADR-006. Implement it for Anthropic first OR OpenAI first (decision deferred), but ensure the abstraction allows swapping or running both behind a flag.

**Provider selection is deferred** until we have a working prototype against one LLM and can compare cost + quality empirically.

## Provider Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Anthropic Claude (Haiku 4.5 or Sonnet)** | Excellent instruction following, structured output via tool calls, large context window for activity history, generous safety guarantees | Pricing per token slightly higher than budget OpenAI tiers; smaller market presence in some regions |
| **OpenAI (GPT-5-mini class)** | Often cheaper at scale, very fast small models, mature SDK | Output quality varies more between model versions, less predictable behavior on long instructions |
| **Both behind a flag** | Compare quality and cost empirically; resilience if one provider has an outage | Two integrations to maintain; doubles the prompt engineering work |
| **Self-hosted open model (Llama, Mistral)** | No per-token cost, full control | Need GPU infra; quality gap on nuanced writing; much higher operational complexity |

## Architecture

```typescript
// packages/shared/src/insights/insights-provider.interface.ts
export interface InsightsProvider {
  readonly id: string;            // 'anthropic' | 'openai'
  readonly model: string;

  generateActivityInsight(input: ActivityInsightInput): Promise<ActivityInsight>;
  generateWeeklyDigest(input: WeeklyDigestInput): Promise<WeeklyDigest>;
}

export interface ActivityInsightInput {
  activity: Activity;
  trainingContext: {
    last7DaysTss: number;
    last28DaysTss: number;
    ctl: number;
    atl: number;
    tsb: number;
    bestEffortsBeaten: string[];  // e.g. ["5K PR by 12s"]
    recentSimilarActivities: ActivitySummary[];
  };
}

export interface ActivityInsight {
  headline: string;           // 1 sentence
  body: string;               // 2-4 sentences
  highlights: string[];       // Bulleted achievements
  suggestion?: string;        // Optional coaching tip
  generatedAt: Date;
  providerId: string;
  modelVersion: string;
  inputTokens: number;
  outputTokens: number;
  costCents: number;
}
```

The service composes a structured prompt from `ActivityInsightInput` (no raw GPS data, just derived metrics), calls the provider, validates the response with Zod, and persists the result.

## Caching & Cost Management

Insights are generated **once per activity** and cached forever in a dedicated table:

```prisma
model ActivityInsight {
  activityId    String   @id
  providerId    String   // 'anthropic' | 'openai'
  modelVersion  String
  headline      String
  body          String
  highlights    Json     // string[]
  suggestion    String?
  generatedAt   DateTime @default(now())
  inputTokens   Int
  outputTokens  Int
  costCents     Float
  activity      Activity @relation(fields: [activityId], references: [id], onDelete: Cascade)
}
```

### Triggering Generation

| Strategy | Pros | Cons |
|----------|------|------|
| **On-sync (automatic)** | Insights appear without user action | Wasteful: many activities never get viewed |
| **On-view (lazy)** ✅ | Only pay for activities the user actually looks at | Brief loading state on first view |
| **Manual button** | Maximum cost control | Adds friction; users may not realize the feature exists |

Use **on-view with a 24-hour deferral**: when the user opens an activity detail page, if no insight exists, enqueue a generation job. Show the insight on the next page load (or via SSE). This gives near-real-time UX while batching well.

Free tier (if introduced) can cap insights at N per month; paid tier unlimited.

### Per-User Cost Estimate

Rough order-of-magnitude (subject to provider choice):

- Input: ~800 tokens (activity + training context)
- Output: ~150 tokens (headline + body + highlights)
- Cost per insight: $0.001-0.005 depending on model tier

An active user with 4 activities/week views ~16/month → $0.02-0.08/month in LLM cost. Sustainable.

## Prompt Strategy (high level)

1. System prompt: "You are a thoughtful coach analyzing one workout against the athlete's recent training history. Be specific, never invent numbers, cite the data when relevant."
2. Structured input: activity stats + training context as JSON
3. Output schema: enforced via tool calls (Anthropic) or JSON mode (OpenAI), validated by Zod on receipt
4. Guardrails: refuse to give medical advice; flag concerning patterns (e.g., 3+ weeks of overreaching) for the user but don't diagnose

## Failure Modes

| Failure | Handling |
|---------|----------|
| Provider API down | Job retries with backoff; insight remains absent (not an error to the user) |
| Rate limit hit | BullMQ rate limiter on the insights queue; degrade gracefully |
| Output fails schema validation | Retry once; on second failure, log and skip (do not show malformed insight) |
| Cost spike | Monthly budget alert via Sentry; automatic queue pause if budget exceeded |

## Consequences

### Positive
- Differentiator vs. Strava: our insights are grounded in derived metrics, not just raw distance/pace
- Provider-agnostic from day one; can switch or A/B test
- Cache + on-view trigger keeps cost predictable
- Persisted insights become a long-term record of the athlete's training story

### Negative
- Adds an external dependency on an LLM provider
- LLM output is inherently nondeterministic; testing is harder than for analytical code
- Prompt engineering becomes a maintained artifact, not a one-off

### Risks
- LLM hallucination: if the model invents numbers, users lose trust. Mitigate with strict input schema + post-hoc validation that any cited number appears in the input.
- Provider pricing changes: monitor monthly cost; the abstraction lets us migrate if needed.
