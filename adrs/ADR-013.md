# ADR-013: Webhook Reliability & Idempotency

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

Strava delivers webhook events with at-least-once semantics: if our endpoint is slow or returns an error, Strava will retry. This means the same event can arrive multiple times. Additionally, the webhook handler must respond within 2 seconds (Strava requirement), so all processing must be deferred to background jobs. If the BullMQ enqueue step fails after returning 200, we lose the event. If we process a duplicate event, we waste resources or create inconsistent state.

## Decision

Implement an **idempotency log** (`WebhookEvent` table) that records every incoming webhook event by provider + event ID. Events are stored before being enqueued, and workers check the log before processing.

## The Problem (Without Idempotency)

```
Strava sends: activity.create (id: 12345)
  → Handler returns 200, enqueues job
  → Network hiccup: Strava doesn't see the 200
  → Strava retries: activity.create (id: 12345) again
  → Handler enqueues a second job
  → Activity is processed twice (duplicate data, double DailyMetrics increment)
```

## The Solution

```
Strava sends: activity.create (id: 12345)
  → Handler checks WebhookEvent table for (strava, 12345)
  → Not found: insert event, enqueue job, return 200
  → Strava retries: activity.create (id: 12345)
  → Handler checks WebhookEvent table for (strava, 12345)
  → Found: skip enqueue, return 200 immediately
```

## Schema

```prisma
model WebhookEvent {
  id          String   @id @default(cuid())
  provider    String   // 'strava'
  eventId     String   // Provider's unique event identifier
  eventType   String   // 'activity.create' | 'activity.update' | 'activity.delete'
  payload     Json
  processedAt DateTime?
  createdAt   DateTime @default(now())

  @@unique([provider, eventId])
  @@index([createdAt])
}
```

## Webhook Handler Flow

```typescript
async handleStravaWebhook(payload: StravaWebhookPayload): Promise<void> {
  const eventId = `${payload.object_type}_${payload.aspect_type}_${payload.object_id}`;

  // 1. Check idempotency
  const existing = await this.prisma.webhookEvent.findUnique({
    where: { provider_eventId: { provider: 'strava', eventId } },
  });
  if (existing) return; // Already processed or in-flight

  // 2. Store event (before enqueue, so we don't lose it)
  await this.prisma.webhookEvent.create({
    data: { provider: 'strava', eventId, eventType: payload.aspect_type, payload },
  });

  // 3. Enqueue for background processing
  await this.syncQueue.add('activity-sync', {
    provider: 'strava',
    webhookEventId: eventId,
    payload,
  });
}
```

## Cleanup

Old webhook events are cleaned up by a scheduled job:
- Events older than 30 days are deleted
- This prevents the table from growing unboundedly
- The 30-day window is generous enough to cover any replay scenario

## Consequences

### Positive
- Duplicate webhook deliveries are harmless (idempotent)
- Events are persisted before enqueue, so a BullMQ failure doesn't lose the event (a recovery job can scan for un-processed events)
- Full audit trail of all webhook events for debugging

### Negative
- Extra database write on every webhook (fast, since it's a simple insert)
- Cleanup job must be scheduled and maintained
- Constructing a unique `eventId` requires understanding each provider's payload structure
