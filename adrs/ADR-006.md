# ADR-006: Adapter Architecture: NestJS Modules with a Shared Interface

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

The platform must support multiple fitness data providers (Strava, Garmin, Apple Health, Polar) without coupling business logic to any single provider. Each provider has different APIs, authentication models, data formats, and rate limits. The core domain (analytics, dashboard, user management) must remain provider-agnostic.

## Decision

Define a shared **`FitnessProvider` interface** in `packages/shared`. Each provider is implemented as a standalone **NestJS module** in `apps/api/src/providers/`. A **`ProviderRegistry`** service uses NestJS dependency injection to manage which providers are enabled per user.

## Interface Definition

```typescript
// packages/shared/src/adapters/provider.interface.ts
export interface FitnessProvider {
  readonly id: string; // 'strava' | 'garmin' | 'apple-health'
  readonly displayName: string;

  getActivities(userId: string, since?: Date): Promise<Activity[]>;
  getActivityDetail(userId: string, externalId: string): Promise<ActivityDetail>;
  getAthleteProfile(userId: string): Promise<AthleteProfile>;
  refreshToken(userId: string): Promise<void>;
  handleWebhook?(payload: unknown): Promise<WebhookEvent | null>;
}
```

## Canonical Domain Model

```typescript
// packages/shared/src/domain/activity.ts
export interface Activity {
  id: string;
  externalId: string; // Strava's ID, Garmin's ID, etc.
  source: string; // 'strava' | 'garmin'
  userId: string;
  type: ActivityType; // 'run' | 'ride' | 'swim' | 'walk' | ...
  startedAt: Date;
  durationSeconds: number;
  distanceMeters: number;
  elevationGainMeters?: number;
  avgHeartRateBpm?: number;
  maxHeartRateBpm?: number;
  avgPaceSecondsPerKm?: number;
  avgWatts?: number;
  calories?: number;
  polyline?: string;
  laps?: Lap[];
  streams?: ActivityStream;
}
```

## Consequences

### Positive

- Business logic (analytics, dashboard) never imports from any provider module
- Adding a new provider is an isolated task: implement the interface, register the module
- Each adapter encapsulates its own API quirks, rate limits, and data mapping
- Testing is straightforward: mock the interface, no need to stub HTTP calls in business logic tests

### Negative

- Interface must be general enough to cover all providers, which may mean some fields are optional or under-utilized for certain sources
- Normalization logic per adapter can be complex (e.g., Garmin's activity types don't map 1:1 to Strava's)

### Implementation Notes

- Each adapter lives in `apps/api/src/providers/{name}/`
- The `ProviderRegistry` resolves adapters by provider ID at runtime
- Webhook handling is optional (Apple Health doesn't push; it's a file import)
- See `docs/ADAPTER_DEVELOPMENT_GUIDE.md` for the full guide on building a new adapter
