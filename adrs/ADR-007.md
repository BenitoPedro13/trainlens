# ADR-007: Frontend Data Fetching: TanStack Query + Server Components

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

The frontend needs to fetch analytics data from the NestJS REST API. Some pages benefit from server-side rendering (fast initial load, SEO), while others require interactive client-side updates (date pickers, filter toggles, chart drill-downs). We need a strategy that supports both.

## Decision

Use **Next.js Server Components** for initial page loads and **TanStack Query** for client-side interactivity and cache management.

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **TanStack Query + Server Components** ✅ | Server Components for fast first paint, TanStack Query for client-side refetch/caching, great stale-while-revalidate | Two mental models (server vs client fetching) |
| **SWR** | Simple, lightweight | Less powerful caching, no query invalidation groups |
| **tRPC** | End-to-end type safety | Tight coupling between Next.js and NestJS; hard to add mobile clients later |
| **GraphQL (Apollo)** | Flexible queries, partial data fetching | Massive overhead, complex caching, overkill for this use case |

## Consequences

### Positive
- Dashboard pages render on the server with fresh data (no loading spinners on first visit)
- Interactive elements (date range selector, sport filter) use TanStack Query for instant client-side updates
- TanStack Query's cache invalidation makes it easy to refresh data after a sync completes
- REST API remains simple and reusable for future mobile clients

### Negative
- Developers must decide per-component whether to fetch on the server or client
- TanStack Query hydration from server components requires careful setup

### Guidelines
- **Server Components**: analytics pages, dashboard overview, activity detail pages
- **TanStack Query (client)**: date pickers, interactive filters, charts with drill-down, real-time sync status
