# ADR-020: Training Plans Engine

> **Status:** Accepted
> **Date:** 2026-05-20

## Context

Training plans turn an analytics platform into a coach. Athletes don't just want to know what they did; they want a structured plan that tells them what to do next.

Strava offers training plans (and acquired Runna for personalized running plans). To match this, TrainLens needs:

- Plan templates for common goals (5K, 10K, half marathon, marathon, base building, cycling FTP build)
- Workout-level prescriptions with pace/HR/power targets
- Calendar assignment (this workout goes on this date)
- Reschedule and skip support
- **Adherence tracking**: automatically match synced activities to planned workouts and compute completion

Adherence is the killer feature. It is what tells a user "you completed 4 of 5 planned workouts this week, including hitting your tempo pace within ±5%."

## Decision

Build a **template-driven plan engine** where plans are composed of weeks, weeks of workouts, and workouts of structured intervals. Once instantiated for a user, plans are mutable (reschedule, skip, swap). Adherence is computed by an automated matcher that pairs activities with their nearest planned workout.

## Schema

```prisma
// Template — reusable across users
model PlanTemplate {
  id           String          @id @default(cuid())
  name         String          // "Beginner Half Marathon — 12 weeks"
  goal         String          // 'half_marathon' | 'marathon' | 'base' | 'ftp_build'
  sport        String          // 'run' | 'ride'
  level        String          // 'beginner' | 'intermediate' | 'advanced'
  durationWeeks Int
  description  String
  weeks        PlanWeekTemplate[]

  @@index([sport, goal, level])
}

model PlanWeekTemplate {
  id           String                @id @default(cuid())
  templateId   String
  weekNumber   Int                   // 1..durationWeeks
  focus        String?               // "Base", "Build", "Peak", "Taper"
  template     PlanTemplate          @relation(fields: [templateId], references: [id], onDelete: Cascade)
  workouts     PlanWorkoutTemplate[]

  @@unique([templateId, weekNumber])
}

model PlanWorkoutTemplate {
  id              String           @id @default(cuid())
  weekTemplateId  String
  dayOfWeek       Int              // 0=Mon..6=Sun
  type            WorkoutType
  name            String           // "Tempo run with 3x10min @ threshold"
  description     String
  // Structured intervals stored as JSON, parsed at runtime
  structure       Json             // Array of { type, durationSeconds?, distanceMeters?, targetType, targetValue, targetTolerance }
  weekTemplate    PlanWeekTemplate @relation(fields: [weekTemplateId], references: [id], onDelete: Cascade)

  @@index([weekTemplateId, dayOfWeek])
}

enum WorkoutType {
  EASY            // Recovery / aerobic
  LONG            // Long run / ride
  TEMPO           // Sustained threshold effort
  INTERVALS       // Repeats above threshold
  HILLS           // Climbing-focused
  RECOVERY        // Very easy
  CROSS_TRAINING  // Non-primary sport
  REST            // No workout planned
  RACE
}

// Instance — a user's enrollment in a plan
model UserPlan {
  id             String           @id @default(cuid())
  userId         String
  templateId     String
  startDate      DateTime         @db.Date
  targetEventDate DateTime?       @db.Date   // For race-targeted plans
  status         UserPlanStatus
  createdAt      DateTime         @default(now())
  completedAt    DateTime?
  user           User             @relation(fields: [userId], references: [id], onDelete: Cascade)
  template       PlanTemplate     @relation(fields: [templateId], references: [id])
  workouts       PlannedWorkout[]

  @@index([userId, status])
}

enum UserPlanStatus {
  ACTIVE
  COMPLETED
  ABANDONED
}

// Concrete workouts on dates, generated from the template on enrollment
model PlannedWorkout {
  id              String          @id @default(cuid())
  userPlanId      String
  scheduledDate   DateTime        @db.Date
  type            WorkoutType
  name            String
  description     String
  structure       Json
  status          WorkoutStatus
  // Adherence (set when matched to an activity)
  matchedActivityId  String?      @unique
  adherenceScore  Float?          // 0-1, see scoring below
  notes           String?         // User notes
  rescheduledFrom DateTime?       @db.Date  // For audit trail
  userPlan        UserPlan        @relation(fields: [userPlanId], references: [id], onDelete: Cascade)
  matchedActivity Activity?       @relation(fields: [matchedActivityId], references: [id])

  @@index([userPlanId, scheduledDate])
  @@index([scheduledDate, status])
}

enum WorkoutStatus {
  UPCOMING
  COMPLETED
  PARTIAL          // Done but didn't hit targets
  MISSED
  SKIPPED          // User explicitly skipped
}
```

## Adherence Matching

When an activity is synced, the matcher runs:

```
1. Find candidate PlannedWorkout rows:
   - Same user
   - scheduledDate within ±2 days of activity.startedAt
   - status = UPCOMING or PARTIAL
   - Compatible sport type

2. Score each candidate (0-1):
   - Date proximity (1.0 if same day, 0.7 if ±1 day, 0.4 if ±2 days)
   - Type match (1.0 if workout type matches activity intensity profile, partial otherwise)
   - Duration match (1.0 if within 20% of planned duration)
   - Target match (e.g., tempo pace within ±5% = 1.0)

3. If best candidate score > 0.6, mark the workout COMPLETED (or PARTIAL if < 0.85) and link it
4. Otherwise, leave the workout UPCOMING and the activity unmatched
```

Users can also manually link an activity to a planned workout if the matcher gets it wrong.

## Reschedule & Skip

- **Skip**: mark `status = SKIPPED`, set `notes` to reason if provided. Does not affect future workouts.
- **Reschedule**: update `scheduledDate`, store `rescheduledFrom` for the audit trail. Plan duration stays the same; the workout just moves.
- **Swap**: change `type`/`structure` to a different workout. Common when life intervenes ("can't do my long run today, doing an easy run instead").
- **Plan abandonment**: set `UserPlan.status = ABANDONED`. Remaining workouts marked as such; no further matching attempted.

## Plan Adherence Dashboard

For each `UserPlan`, the dashboard shows:

- Overall completion rate (%)
- Week-by-week breakdown (5/6 workouts completed this week)
- Pace trend on similar workout types (am I getting faster on tempo runs over the plan?)
- Days until target event (if applicable)
- Upcoming workouts in next 7 days

## Consequences

### Positive
- Templates can be reused, versioned, and tested independently of user enrollments
- Structured workout `structure` JSON enables target-vs-actual analysis (interval-level adherence)
- The matcher reuses already-computed activity data; no expensive recomputation
- Plan abandonment is a first-class state (no orphaned workouts)

### Negative
- Plan UX is the most complex feature in the platform. Budget time for the UI as much as the backend.
- Template authoring is currently manual. Long-term, AI-generated personalized plans (à la Runna) are a separate effort.
- Workout `structure` JSON is schema-less in the database; document the shape carefully in `docs/TRAINING_PLANS.md`.

### Risks
- Matcher false positives: an unrelated activity gets matched to a planned workout. Mitigate with a confidence threshold and a "wrong match" button in the UI that updates the matcher's calibration over time.
- Matcher false negatives: a clearly-completed workout is missed. Mitigate with manual link button.
