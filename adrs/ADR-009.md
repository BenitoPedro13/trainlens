# ADR-009: Observability: Pino + Sentry + Bull Board

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

Without structured logging, error tracking, and job monitoring, production debugging becomes guesswork. The platform has multiple layers where things can fail silently: API requests, background sync jobs, webhook processing, analytics recalculation, and token refresh flows. Observability must be a day-one concern, not a Phase 2 afterthought.

## Decision

Implement a three-layer observability stack from the start:

1. **Pino** for structured JSON logging across the NestJS API
2. **Sentry** for exception tracking with context (both API and frontend)
3. **Bull Board** for BullMQ job monitoring and queue health

Metrics (Prometheus + Grafana) are deferred to Phase 2 when traffic patterns are understood.

## Options Considered

### Logging

| Option | Pros | Cons |
|--------|------|------|
| **Pino** ✅ | Fastest Node.js logger, JSON output by default, great NestJS integration via `nestjs-pino` | Less human-readable in dev (mitigated by `pino-pretty`) |
| **Winston** | Feature-rich, widely used | Slower, heavier, more configuration |
| **Console.log** | Zero setup | No structure, no correlation, impossible to search |

### Error Tracking

| Option | Pros | Cons |
|--------|------|------|
| **Sentry** ✅ | Industry standard, source maps, breadcrumbs, performance monitoring, generous free tier | Paid at scale |
| **Bugsnag** | Good alternative | Smaller ecosystem |
| **Self-hosted (ELK)** | Full control | Massive operational overhead for a small team |

### Job Monitoring

| Option | Pros | Cons |
|--------|------|------|
| **Bull Board** ✅ | Purpose-built for BullMQ, web UI, easy to deploy | Basic UI; no alerting built in |
| **Arena** | Alternative BullMQ dashboard | Less maintained |
| **Custom dashboard** | Full control | Development time wasted on non-core features |

## Implementation Details

### Structured Logging with Pino

Every log entry includes:
- `requestId`: unique per HTTP request (generated by middleware)
- `userId`: extracted from JWT (when authenticated)
- `correlationId`: traces a job from webhook receipt through sync to analytics recalc
- `provider`: which adapter is involved ('strava', 'garmin')
- `jobId`: BullMQ job ID (in worker contexts)

```typescript
// Example log output
{
  "level": "info",
  "time": 1716134400000,
  "requestId": "req_abc123",
  "userId": "usr_xyz",
  "provider": "strava",
  "msg": "Activity synced successfully",
  "activityId": "act_456",
  "durationMs": 234
}
```

### Sentry Integration
- NestJS: global exception filter reports unhandled errors with full request context
- Next.js: Sentry SDK with source maps for frontend errors
- BullMQ workers: wrap each job processor in a Sentry transaction
- Include `userId`, `provider`, and `jobId` as Sentry tags for filtering

### Bull Board
- Deployed as a separate service (or route) behind authentication
- Shows queue health: waiting, active, completed, failed, delayed counts
- Failed jobs are inspectable with full error stack and payload

### Health Checks
- `/health` endpoint using NestJS Terminus
- Checks: database connectivity, Redis connectivity, queue responsiveness
- Used by Docker health checks and load balancer probes

## Consequences

### Positive
- Every production issue has a trail: request ID, correlation ID, timestamps
- Failed sync jobs are visible and retryable from Bull Board
- Sentry alerts on new error types before users report them
- Health checks enable automated restart on infrastructure failures

### Negative
- Pino's JSON output is less readable during local development (use `pino-pretty` in dev)
- Sentry adds a small runtime overhead (negligible for this workload)
- Bull Board is another service to deploy and secure
