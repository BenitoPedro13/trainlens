# ADR-017: Segment Data Model & Sync

> **Status:** Accepted
> **Date:** 2026-05-20

## Context

Segments are one of Strava's defining features: short stretches of road or trail that athletes repeatedly attempt, with leaderboards for the fastest times. They are first-class entities, not properties of an activity. The same segment can be attempted by thousands of athletes, and a single activity can include efforts on many segments.

To compete with Strava as an analytics platform, TrainLens needs:

- A user's segment efforts (every time they crossed a segment, with their time, HR, power)
- Personal segment progression: am I getting faster on my home loop?
- Filtered leaderboards (vs. people in my age, weight, gender)
- Side-by-side effort comparison on the same segment

The Strava API provides this data, but it is structured differently from activities and has its own sync pattern.

## Decision

Treat **segments and segment efforts as first-class entities** in their own tables, sync them as part of activity detail fetches, and store leaderboards lazily on demand.

## Data Model

```prisma
model Segment {
  id              String   @id @default(cuid())
  source          String   // 'strava'
  externalId      String   // Strava segment ID
  name            String
  activityType    String   // 'run' | 'ride'
  distanceMeters  Float
  averageGrade    Float?
  maxGrade        Float?
  elevationHigh   Float?
  elevationLow    Float?
  totalElevation  Float?
  city            String?
  state           String?
  country         String?
  // polyline + start/end points stored via raw SQL (see ADR-016)
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
  efforts         SegmentEffort[]

  @@unique([source, externalId])
  @@index([activityType])
}

model SegmentEffort {
  id              String   @id @default(cuid())
  userId          String
  activityId      String
  segmentId       String
  externalId      String   // Strava segment_effort ID
  elapsedSeconds  Int      // Total time including stops
  movingSeconds   Int      // Time actually moving
  startedAt       DateTime
  avgHeartRate    Int?
  maxHeartRate    Int?
  avgWatts        Float?
  avgCadence      Float?
  prRank          Int?     // 1, 2, 3 if this was a top-3 personal effort
  komRank         Int?     // 1-10 if it's a KOM/QOM ranking at sync time
  achievementCount Int     @default(0)
  user            User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  activity        Activity @relation(fields: [activityId], references: [id], onDelete: Cascade)
  segment         Segment  @relation(fields: [segmentId], references: [id])

  @@unique([source, externalId])
  @@index([userId, segmentId, startedAt])  // "all my efforts on segment X over time"
  @@index([userId, startedAt])
  @@index([segmentId, elapsedSeconds])     // Leaderboard queries
}

// Lazy-fetched leaderboards (Strava API returns them per-segment)
model SegmentLeaderboardSnapshot {
  segmentId   String
  filterHash  String   // Hash of filter params (age, gender, weight, time window)
  payload     Json     // Top N entries from Strava
  fetchedAt   DateTime @default(now())

  @@id([segmentId, filterHash])
  @@index([fetchedAt])  // For cleanup
}
```

## Sync Flow

1. **During activity detail fetch**: Strava returns `segment_efforts` inline. For each effort:
   - Upsert the `Segment` (if first time seeing it)
   - Insert the `SegmentEffort`
2. **Segment metadata**: when a segment is first seen, do a lightweight call to `/segments/{id}` for full details (polyline, elevation profile). Cache aggressively; segments rarely change.
3. **Leaderboards**: fetched on demand when a user views a segment page. Cache for 1 hour to keep API cost bounded.

## Rate Limit Implications

Strava's rate limits (100 req / 15min, 1000 req / day per user) apply to segment endpoints as well. Mitigations:

- During bulk import, segment efforts come **for free** inside activity detail responses. No extra calls needed.
- Segment metadata fetches are batched by a dedicated BullMQ queue (`segment-metadata-sync`) with low concurrency
- Leaderboard fetches are user-triggered (one per page view); cache them for 1 hour to avoid hammering

## Why Lazy Leaderboards

Leaderboards change constantly as athletes worldwide log efforts. Pre-syncing them is wasteful: the user may never view that segment's leaderboard. Lazy fetch + short cache balances freshness with cost.

A 1-hour TTL also makes filtered leaderboards practical: if a user toggles "M, 30-34, under 70kg", we hit the API once and serve subsequent toggles from cache.

## Consequences

### Positive
- Segment efforts are queryable as a first-class time series ("my times on this segment over the last year")
- Reuses the activity sync pipeline; no new external integration work
- Leaderboard caching limits API cost
- Spatial polyline storage (via ADR-016) enables future features like "show all segments inside this map region"

### Negative
- Storage grows with each activity (a single ride can have 50+ segment efforts)
- Segment table can get very large for active users (mitigation: nothing required short term, partitioning is an option)
- Leaderboard cache must respect Strava's data attribution requirements

### Risks
- Strava's API terms forbid certain redistributions of segment data. Before exposing segment leaderboards publicly (vs. only to the user who logged the efforts), review the terms.

## Implementation Notes

- Add to existing `ActivityRawPayload` storage (ADR-010) so we can re-extract segment efforts if normalization improves
- Use the same idempotency strategy as activity sync: `(source, externalId)` uniqueness on both Segment and SegmentEffort
- Segment polyline is stored as `geography(LINESTRING, 4326)` via raw SQL (see ADR-016)
