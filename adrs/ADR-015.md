# ADR-015: Testing Strategy

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

The platform has multiple layers where bugs can hide: adapter normalization logic, analytics formulas (CTL/ATL/TSB calculations), API endpoints, background job flows, and frontend rendering. Without a clear testing strategy, confidence in deployments drops as the codebase grows. We also need to test Strava API interactions without hitting real endpoints or burning rate limits.

## Decision

Adopt a **multi-layer testing strategy** using Jest for unit and integration tests, recorded HTTP fixtures for adapter tests, Testcontainers for realistic database tests, and Playwright for critical E2E flows.

## Testing Layers

### Unit Tests (Jest)

**What:** Pure functions with no external dependencies.

**Scope:**
- Analytics formulas: TSS calculation, CTL/ATL/TSB exponential moving averages, zone boundary computation
- Normalization logic: Strava activity type mapping, pace/speed conversion, polyline encoding
- Domain utilities: streak detection, monotony ratio, acute-to-chronic ratio
- Shared type validators

**Guidelines:**
- No database, no network, no Redis
- Fast: entire suite runs in <10 seconds
- High coverage on analytics formulas (these are the product's core value)

### Integration Tests (Jest + Testcontainers)

**What:** Tests that touch real infrastructure (PostgreSQL, Redis) via Testcontainers.

**Scope:**
- API endpoint tests: request in, response out, database state verified
- Database queries: especially raw SQL queries for TimescaleDB functions
- BullMQ job flows: enqueue, process, verify database side effects
- DailyMetrics recalculation after activity create/update/delete
- Webhook idempotency: verify duplicate events are skipped

**Guidelines:**
- Testcontainers spin up real PostgreSQL (with TimescaleDB) and Redis per test suite
- Each test gets a clean database (transaction rollback or truncation)
- Slower than unit tests but catch real query bugs that mocks would miss

### Adapter Tests (Jest + nock or msw)

**What:** Tests for provider adapters against recorded HTTP fixtures.

**Scope:**
- Strava API responses: activity list, activity detail, athlete profile
- Token refresh flow: expired token triggers refresh, retries original request
- Error handling: rate limit responses (429), server errors (500), revoked tokens (401)
- Normalization: verify that a real Strava payload maps correctly to the canonical Activity model

**Guidelines:**
- Record real Strava API responses once, commit them as fixtures (scrub any real tokens/IDs)
- Use `nock` or `msw` to intercept HTTP calls and return fixtures
- Never hit the real Strava API in CI
- Update fixtures when Strava's API changes (check periodically)

### E2E Tests (Playwright)

**What:** Full browser tests against a running instance of the entire stack.

**Scope:**
- Login flow (mocked OAuth redirect)
- Connect Strava (mocked OAuth)
- Dashboard loads with data
- Activity detail page renders
- Settings: disconnect provider, delete account

**Guidelines:**
- Run against Docker Compose with seeded test data
- Keep the suite small: 5-10 critical paths, not exhaustive
- Run in CI on every PR (headless)
- Visual regression is deferred (not worth the maintenance cost at this stage)

### Contract Tests (TypeScript compiler)

**What:** Ensure shared types in `packages/shared` haven't drifted from their consumers.

**Scope:**
- `FitnessProvider` interface: if the interface changes, all adapters must update
- `Activity` domain model: if fields change, both API and web must handle it
- API response types: shared between NestJS controllers and TanStack Query hooks

**Guidelines:**
- TypeScript strict mode (`strict: true`) in all packages
- CI runs `tsc --noEmit` across the entire monorepo
- This is not a test framework; it's the compiler catching drift

## Test File Conventions

```
apps/api/src/analytics/
  analytics.service.ts
  analytics.service.spec.ts         # Unit tests
  analytics.service.integration.ts  # Integration tests (Testcontainers)

apps/api/src/providers/strava/
  strava.adapter.ts
  strava.adapter.spec.ts            # Adapter tests (fixtures)
  fixtures/
    activity-list.json
    activity-detail.json
    rate-limit-response.json

apps/web/e2e/
  dashboard.spec.ts                 # Playwright E2E
  login.spec.ts
```

## CI Pipeline

```
1. Lint (ESLint + Prettier)         ~30s
2. Type check (tsc --noEmit)        ~20s
3. Unit tests (Jest)                ~10s
4. Adapter tests (Jest + nock)      ~15s
5. Integration tests (Testcontainers) ~60s
6. E2E tests (Playwright)          ~120s
```

Total target: under 5 minutes for the full pipeline.

## Consequences

### Positive
- Analytics formulas have high test coverage, protecting the product's core value
- Testcontainers catch real database bugs (TimescaleDB-specific queries, index usage)
- Recorded fixtures make adapter tests fast and deterministic
- E2E tests catch integration issues between frontend and API
- TypeScript strict mode prevents type drift across the monorepo

### Negative
- Testcontainers are slower than mocked tests (mitigated by running in parallel)
- HTTP fixtures can become stale if Strava changes their API format
- E2E tests are the most fragile and expensive to maintain
- Initial setup of Testcontainers and Playwright requires some effort
