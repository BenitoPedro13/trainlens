# ADR-011: Token & Key Management

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

The platform stores OAuth access and refresh tokens for each user's connected providers (Strava, Garmin, etc.). These tokens grant access to the user's fitness data and must be protected at rest. A compromised encryption key would expose every user's tokens, so key management needs a rotation strategy from the start.

## Decision

Use **AES-256-GCM envelope encryption**: each user's tokens are encrypted with a unique Data Encryption Key (DEK), and each DEK is itself encrypted (wrapped) by a master Key Encryption Key (KEK).

## Options Considered

| Option                                 | Pros                                                                                           | Cons                                                                                |
| -------------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **Envelope encryption (DEK + KEK)** ✅ | Per-user keys; master key rotation doesn't require re-encrypting all tokens; industry standard | More complex implementation than a single key                                       |
| **Single application-wide key**        | Simplest; one env var                                                                          | If compromised, all tokens are exposed; rotation requires re-encrypting every token |
| **Cloud KMS (AWS KMS, GCP KMS)**       | Hardware-backed keys, audit trail, automatic rotation                                          | Cloud vendor dependency; adds latency to every decrypt; cost                        |
| **Vault (HashiCorp)**                  | Full secrets management                                                                        | Heavy infrastructure for early stage                                                |

## Envelope Encryption Flow

```
Encrypt:
1. Generate a random 256-bit DEK for the user (on first connection)
2. Encrypt the OAuth tokens with DEK using AES-256-GCM
3. Encrypt the DEK with the master KEK
4. Store: encrypted tokens + encrypted DEK + IV + auth tag in Connection table

Decrypt:
1. Load encrypted DEK from Connection table
2. Decrypt DEK using master KEK
3. Decrypt OAuth tokens using DEK
```

## Master KEK Management

| Environment            | KEK Storage                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Local dev**          | Environment variable (`TOKEN_ENCRYPTION_KEY`)                                                                   |
| **Staging/Production** | Cloud secrets manager (AWS Secrets Manager, GCP Secret Manager, or platform-native like Railway/Render secrets) |
| **Future**             | Cloud KMS for hardware-backed key protection                                                                    |

### Key Rotation Procedure

1. Generate a new master KEK
2. Run a background job that re-wraps every user's DEK with the new KEK
3. Once all DEKs are re-wrapped, decommission the old KEK
4. Individual user token re-encryption is never needed (only the DEK wrapper changes)

## Consequences

### Positive

- Compromising one user's DEK exposes only that user's tokens
- Master key rotation is fast (re-wrap DEKs, not re-encrypt all tokens)
- AES-256-GCM provides both confidentiality and integrity (authenticated encryption)
- Migration path to cloud KMS is straightforward (KMS becomes the KEK)

### Negative

- More implementation complexity than a single key
- DEK storage adds columns to the Connection table
- Developers must understand the two-layer model

### Risks

- Master KEK in environment variables is a single point of failure in production. Mitigate by moving to a secrets manager as early as possible.
