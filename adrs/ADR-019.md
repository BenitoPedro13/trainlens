# ADR-019: Goals & Targets System

> **Status:** Accepted
> **Date:** 2026-05-20

## Context

Athletes train with intent: hit 50 km this week, ride 5000 km this year, beat a 5K PR by August, climb 10000 m of elevation. Without a system for setting and tracking goals, an analytics platform shows you where you are but not where you want to be.

Strava Premium offers custom goals across multiple dimensions (distance, time, count, segment time, power). To match and exceed this, TrainLens needs:

- A flexible goal schema covering all common goal types
- Automatic progress computation from existing activity data
- Time-window awareness (this week vs this month vs this year)
- Notifications on milestones and at-risk goals

## Decision

Implement a **goal-as-data** system where each goal is a row with a type, target, time window, and computed progress. Progress is recomputed incrementally on every sync that affects the goal's window.

## Schema

```prisma
model Goal {
  id              String     @id @default(cuid())
  userId          String
  type            GoalType   // enum
  sportType       String?    // null = all sports; or 'run' | 'ride' | etc.
  targetValue     Float      // The number being aimed at
  unit            String     // 'meters' | 'seconds' | 'count' | 'tss' | 'watts' | 'bpm'
  period          GoalPeriod // 'WEEK' | 'MONTH' | 'YEAR' | 'CUSTOM'
  periodStart     DateTime   // Inclusive
  periodEnd       DateTime   // Inclusive
  segmentId       String?    // Only for type = 'SEGMENT_TIME'
  status          GoalStatus // 'ACTIVE' | 'COMPLETED' | 'FAILED' | 'CANCELLED'
  createdAt       DateTime   @default(now())
  completedAt     DateTime?
  user            User       @relation(fields: [userId], references: [id], onDelete: Cascade)
  progress        GoalProgress?

  @@index([userId, status])
  @@index([userId, periodEnd])  // For "what's expiring soon"
}

enum GoalType {
  DISTANCE          // Sum of distanceMeters over period
  DURATION          // Sum of durationSeconds over period
  ACTIVITY_COUNT    // Number of activities over period
  TSS               // Sum of TSS over period
  ELEVATION         // Sum of elevationGainM over period
  STREAK            // Consecutive days with at least one activity
  SEGMENT_TIME      // Beat target time on a specific segment
  BEST_EFFORT       // Achieve target time at a standard distance (e.g., sub-20 5K)
}

enum GoalPeriod {
  WEEK
  MONTH
  YEAR
  CUSTOM
}

enum GoalStatus {
  ACTIVE
  COMPLETED
  FAILED       // Period ended without hitting target
  CANCELLED    // User cancelled the goal
}

// Denormalized progress for fast reads
model GoalProgress {
  goalId          String   @id
  currentValue    Float
  percentage      Float    // 0-100+
  lastActivityAt  DateTime?
  // For STREAK type
  currentStreak   Int?
  longestStreak   Int?
  // Pacing
  daysRemaining   Int
  paceStatus      String   // 'ahead' | 'on-track' | 'behind' | 'at-risk'
  updatedAt       DateTime @updatedAt
  goal            Goal     @relation(fields: [goalId], references: [id], onDelete: Cascade)
}
```

## Progress Computation

Two triggers update `GoalProgress`:

1. **On activity sync (incremental)**: when an activity is created, updated, or deleted, find all active goals whose period contains the activity's date and whose type matches, then recompute their progress. This is fast because we already have `DailyMetrics` aggregations.

2. **Scheduled rollover (daily)**: a midnight job (per user's timezone) does two things:
   - Closes out goals whose period ends today (mark `COMPLETED` or `FAILED`)
   - Auto-creates recurring goals if the user enabled rollover (e.g., "every week, hit 50km")
   - Updates `daysRemaining` and `paceStatus` for all active goals

## Pace Status Calculation

For each active goal, derive `paceStatus`:

```
expectedProgress = (daysPassed / totalDays) * targetValue
actualProgress = currentValue

if actualProgress >= targetValue: COMPLETED
elif actualProgress >= expectedProgress * 1.10: 'ahead'
elif actualProgress >= expectedProgress * 0.90: 'on-track'
elif actualProgress >= expectedProgress * 0.70: 'behind'
else: 'at-risk'
```

This gives the user actionable feedback: "you're behind pace on your monthly goal."

## API Surface

```
GET  /api/v1/goals                 List active + recent goals
POST /api/v1/goals                 Create a new goal
GET  /api/v1/goals/:id             Goal detail with progress history
PUT  /api/v1/goals/:id             Update (e.g., revise target)
DELETE /api/v1/goals/:id           Cancel
POST /api/v1/goals/:id/rollover    Convert to recurring
```

## UI Considerations

- Dashboard widget: top 3 active goals with progress bars
- Dedicated `/goals` page with full history
- Goal creation modal with sensible defaults (Sunday-Saturday week, Jan 1-Dec 31 year)
- Sparkline showing cumulative progress vs. ideal pace line

## Consequences

### Positive
- One schema covers all common goal types
- Incremental updates keep progress reads fast
- Pace status gives users early warning, not just final results
- Auto-rollover supports "set it and forget it" recurring goals
- Segment-time and best-effort goals reuse data already computed in other features

### Negative
- Timezone handling is non-trivial: "this week" depends on where the user lives. Store `User.timezone` and use it for period boundaries.
- Recurring goals can pile up if users abandon them; UI should make it easy to bulk-cancel
- Streak goals require special handling (they don't aggregate, they sequence)

### Risks
- Users with very high goal counts (50+) could slow incremental updates. Mitigation: process goal updates in a low-priority BullMQ queue after the main sync completes.
