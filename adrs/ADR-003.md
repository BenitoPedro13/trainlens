# ADR-003: ORM: Prisma

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

We need an ORM or query builder that works well in a TypeScript monorepo, provides type safety, handles migrations, and can be shared between the API and web server components.

## Decision

Use **Prisma** in a `packages/database` shared package. Use `prisma.$queryRaw` for TimescaleDB-specific queries.

## Options Considered

| Option        | Pros                                                                                                                         | Cons                                                                        |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Prisma** ✅ | Type-safe, great migrations, works perfectly in monorepo as shared package, excellent DX, generated types shared across apps | Some complex queries need raw SQL; no native TimescaleDB hypertable support |
| **TypeORM**   | NestJS-native integration, full ORM                                                                                          | More verbose, weaker type inference, messy migration history                |
| **Drizzle**   | Fully type-safe SQL builder, very fast, closer to SQL                                                                        | Younger ecosystem, less tooling, fewer community resources                  |
| **Kysely**    | Type-safe query builder, lightweight                                                                                         | No built-in migrations, you manage schema yourself                          |

## Consequences

### Positive

- Schema defined once in `packages/database`, types generated and shared across `apps/api` and `apps/web`
- Migrations are versioned and reproducible
- IDE autocomplete for all database operations
- Large community and ecosystem (guides, plugins, debugging tools)

### Negative

- Complex analytical queries (rolling averages, window functions) require `$queryRaw`, creating two query patterns
- No native support for TimescaleDB hypertables or continuous aggregates (managed via raw migrations)
- Prisma Client binary adds ~10MB to deployments

### Implementation Notes

Document clearly which queries go through Prisma and which use raw SQL:

- **Prisma**: all CRUD operations, simple filtering, pagination, joins
- **Raw SQL**: `time_bucket()` queries, continuous aggregate management, hypertable creation, complex window functions
