# ADR-010: Raw Activity Data Storage Strategy

> **Status:** Accepted
> **Date:** 2026-05-19

## Context

When syncing activities from providers like Strava, we receive rich JSON payloads (50-100KB each for activities with GPS streams, laps, and segment efforts). Storing these raw payloads is valuable for reprocessing (when we improve normalization logic or add new derived fields), but embedding large JSON blobs in the primary `Activity` table bloats query performance for reads that don't need the raw data.

## Decision

Store raw provider payloads in a **separate `ActivityRawPayload` table** with a 1:1 relationship to `Activity`. The primary `Activity` table contains only normalized, query-optimized fields.

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Separate table** ✅ | Keeps Activity table lean; raw data accessible when needed; easy to add compression or archival policies | Extra join when raw data is needed; slightly more complex schema |
| **JSON column on Activity** | Simplest schema | Bloats the Activity table; every query loads or skips a large column; hard to apply different retention policies |
| **S3/object storage** | Cheapest at scale; infinite storage | Extra infrastructure; higher latency to access; complicates local development |
| **Don't store raw data** | Simplest | Lose the ability to reprocess; if normalization logic improves, old activities are stuck with old mapping |

## Consequences

### Positive
- `Activity` table stays small and fast for analytics queries
- Raw data is available for reprocessing whenever normalization logic improves
- Different retention policies can apply: keep Activity forever, compress/archive raw payloads after 1 year
- The raw payload table can be excluded from backups if storage becomes a concern

### Negative
- Requires a JOIN to access raw data (rare operation, acceptable cost)
- Two tables to maintain instead of one

### Migration Path
- Phase 1: separate table with cascading delete
- Phase 2+: if storage costs grow, add a background job that compresses raw payloads older than N months or moves them to S3, replacing the table row with a reference pointer

## Schema

```prisma
model ActivityRawPayload {
  activityId  String   @id
  payload     Json     // Full provider response
  createdAt   DateTime @default(now())
  activity    Activity @relation(fields: [activityId], references: [id], onDelete: Cascade)
}
```
