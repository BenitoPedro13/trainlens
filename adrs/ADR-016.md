# ADR-016: Spatial Data with PostGIS

> **Status:** Accepted
> **Date:** 2026-05-20

## Context

Several planned features require spatial computation that goes beyond storing encoded polylines:

- **Personal heatmap**: aggregate all GPS points a user has ever recorded into a tile-based visualization (every road and trail they've covered)
- **Matched runs**: detect when two activities cover substantially the same route, then compare efforts side by side
- **Route clustering**: group activities by start/end proximity to find frequently-used routes
- **Segment matching** (future): determine which of a user's activities traversed a given segment
- **Explore radius**: compute the bounding region of a user's typical training area

These are spatial operations: distance between geometries, similarity of polylines, proximity queries, geometric containment. Building them on top of plain Postgres text columns would mean implementing all of this in application code, slowly and incorrectly.

## Decision

Enable the **PostGIS extension** alongside TimescaleDB on the same PostgreSQL database. Store activity GPS data as `geography(LINESTRING, 4326)` geometries, with GIST indexes for spatial queries.

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **PostGIS extension** ✅ | Industry standard, coexists with TimescaleDB, full spatial SQL (ST_DWithin, ST_HausdorffDistance, ST_Buffer), GIST indexes, single database | One more extension to operate; spatial queries can be expensive without careful indexing |
| **App-level spatial code** | No new infrastructure | Reinventing geometry math; slow; error-prone; can't push computation to the DB |
| **Separate spatial DB (MongoDB geo, Elasticsearch geo)** | Purpose-built for geo | Two databases, two backups, two failure modes; cross-DB joins are painful |
| **Tile precomputation only (no extension)** | Simple | Doesn't help with matched runs, route clustering, or any non-heatmap spatial work |

## Coexistence with TimescaleDB

Both extensions are first-party Postgres extensions and are commonly used together. TimescaleDB partitions time-series tables (hypertables on `Activity.startedAt`); PostGIS adds geometry types and spatial indexes to those same tables. No conflict.

## Schema Additions

```prisma
// Activity gets a spatial column (managed via raw SQL migration since Prisma doesn't natively support PostGIS types)
model Activity {
  // ... existing fields
  // route geography(LINESTRING, 4326) -- added via raw migration
}

// New: aggregated points per user for personal heatmap (tile-based)
model UserHeatmapTile {
  userId    String
  z         Int      // Zoom level
  x         Int      // Tile X
  y         Int      // Tile Y
  count     Int      // Number of GPS points in this tile
  updatedAt DateTime @updatedAt

  @@id([userId, z, x, y])
}

// New: route fingerprints for matched-runs detection
model RouteFingerprint {
  id          String   @id @default(cuid())
  userId      String
  activityId  String   @unique
  // fingerprint: geography column with simplified linestring
  // startPoint, endPoint: geography(POINT) columns
  // hash: short hash of decimated polyline for fast bucketing
  hash        String
  createdAt   DateTime @default(now())

  @@index([userId, hash])
  @@index([userId])
}
```

Spatial columns and GIST indexes are added via raw SQL migrations (see ADR-003 on the Prisma + raw SQL pattern):

```sql
-- Migration: add spatial columns
ALTER TABLE "Activity" ADD COLUMN route geography(LINESTRING, 4326);
CREATE INDEX activity_route_gist ON "Activity" USING GIST (route);

ALTER TABLE "RouteFingerprint" ADD COLUMN fingerprint geography(LINESTRING, 4326);
ALTER TABLE "RouteFingerprint" ADD COLUMN start_point geography(POINT, 4326);
ALTER TABLE "RouteFingerprint" ADD COLUMN end_point geography(POINT, 4326);
CREATE INDEX rfp_fingerprint_gist ON "RouteFingerprint" USING GIST (fingerprint);
CREATE INDEX rfp_start_gist ON "RouteFingerprint" USING GIST (start_point);
```

## Matched Runs Algorithm (sketch)

1. When syncing an activity, decode its polyline to GPS points
2. Simplify with Douglas-Peucker (`ST_Simplify`) to reduce point count
3. Compute a coarse hash (e.g., geohash of start + end + decimated midpoints)
4. Store fingerprint in `RouteFingerprint`
5. To find matches: bucket by hash, then use `ST_HausdorffDistance` (or Frechet) to confirm similarity within a threshold (e.g., 50m max deviation over 90% of length)

This is a classic two-stage filter: cheap hash bucketing first, expensive geometry comparison only on candidates.

## Personal Heatmap Strategy

- Decode polyline points on sync
- For each zoom level we want to support (typically 10-15), compute the slippy-map tile containing each point
- Increment `UserHeatmapTile.count` for the user/zoom/tile combination
- Frontend requests tiles for the current viewport via a tile server endpoint that aggregates user tiles

Continuous aggregation is not required since per-tile counts are cheap to maintain incrementally on every sync.

## Consequences

### Positive
- Spatial queries push down to the database, where they belong
- Matched runs, route clustering, and heatmaps all share the same data model
- PostGIS is mature and well-documented; many ORMs (including Prisma via raw SQL) work fine
- Single Postgres instance still serves everything

### Negative
- Another extension to install in dev, staging, and production (most managed Postgres providers offer it; check yours)
- Spatial migrations are managed via raw SQL rather than the Prisma schema
- GIST indexes are larger than B-tree indexes; budget for it
- Computing tile counts on every sync adds work to the sync job

### Risks
- If your eventual hosting provider doesn't support PostGIS (rare but possible), this is harder to undo than TimescaleDB. Verify before choosing a provider.

## Implementation Notes

- Local dev: use the `timescale/timescaledb-ha:pg16` image which includes PostGIS
- For tile rendering, consider `pg_tileserv` or a Node-side library like `@mapbox/sphericalmercator`
- The `route` column can be derived from the existing `polyline` field; backfill via a migration job
